135 pages off WordPress

Homepage, 23 subpages, 109 blog posts, generated by a Python builder. On the main domain since August 2026.

Bravo 6 had a Divi site on WordPress. I rebuilt it as 135 static pages: the homepage, 23 subpages and 109 blog posts. Each page lives in its own folder with an index file, so the clean URLs work on ordinary shared hosting without any rewrite rules.

Two Python scripts do the generating. One builds the subpages from a set of component specs, and the other picks up every captured blog post, pulls out the article body, downloads the images and writes the post pages and the blog index. Adding a post means dropping in a file and running it again.

The two tools in the Resources menu are new. Is It Flyable Today pulls the current METAR for the Rexburg airport through a small PHP proxy and checks it against the school's own written weather minimums rather than generic VFR rules, then shows GO, MARGINAL or NO-GO along with whichever condition caused it. The training area map draws the school's three practice areas, traced from its operating procedures, over an FAA sectional chart in Leaflet.

Every content page carries a single connected schema graph that validates with no errors. The site deploys over FTPS to SiteGround behind Cloudflare, and the stylesheet URL is fingerprinted on each change so returning visitors are not served a cached copy for a year.

Off Wix, rankings intact

Half the content was stuck inside iframes. Rebuilt as real pages, original slugs kept.

On Wix, some of the most important sections of the site were rendered inside iframes, which meant search engines saw the frame and not the text. All of that content is now ordinary HTML on the page.

There are 22 pages. Every slug matches the old site so the existing rankings carried over, the URLs have no extensions, the Tailwind build is compiled to one stylesheet instead of loading from a CDN, and each page carries an organization schema block with the camp's actual name, address and phone number.

The registration form is the biggest piece of custom work. It runs in seven steps with a progress indicator, saves every answer in the browser so a parent can finish later, keeps a running total as rentals and apparel are added, pulls the session tiles from the camp's Salesforce inventory, and only shows the waitlist once a week has actually sold out.

The site went live on the real domain in July 2026. The gallery has more than two hundred of the camp's own photos, converted to WebP.

The site was never slow

Quarter-second TTFB, images already optimized. The actual problems: broken schema, junk sitemap URLs, double-encoded titles, 200KB of builder markup.

The brief said the GoDaddy site was slow, and it was not. Time to first byte was about a quarter of a second, the images were already optimized on a CDN, and there was no autoplay video. The problem was control. GoDaddy's builder had generated a broken business schema block with a made-up domain in it, put junk URLs in the sitemap, double-encoded the page titles, and wrapped about 30KB of content in 247KB of markup.

I rebuilt it as fourteen hand-coded pages using the client's own copy and prices, compressed and self-hosted her photos, and gave every page one schema graph covering the business, the page type, breadcrumbs, and a seven-service offer catalog. There are no review stars in the markup, because marking up your own ratings is against Google's rules.

It has been live on SiteGround since August 2026 with Tag Manager, analytics and Clarity on every page. A crawl after launch came back with no issues: all 211 images have alt text, the structured data validates on every page, and there are no duplicate titles or descriptions.

02 Beyond websites

Applications

Three internal products I built for the agency I work at. They run the place day to day. All three are behind a company sign-in, so screenshots are all I can show here.

Memphis

Sign-in required

memphis.hangarmarketing.com

The agency's project management system. It replaced Asana. Tasks, subtasks, timers, boards, calendars, timelines, KPI dashboards, hours by client, approvals, and a live inbox.

  • A REST API with scoped keys, and an MCP server with 17 tools so tasks can be created, timed and commented on from a chat.
  • Team messaging goes through Slack's API, so a message sent from the app shows up in the real workspace.
  • The old Asana board was imported as an archive of 367 tasks and 841 subtasks, with its columns and tags kept. None of it counts as live work.
  • There is an arcade of multiplayer games built on Firebase's realtime database, with Elo ladders. A test fails the build if a hand's download cost grows, which is what keeps it inside the free allowance.
  • A weekly storage sweep clears uploads whose task has been deleted. It shipped switched off so the counts could be read first.

React 19, TypeScript, Vite, Tailwind, Firebase. Built solo.

Tarmac

Sign-in required

tarmac.hangarmarketing.com

The agency's staff time and operations app, including the timeclock: an iPad kiosk, a phone portal and an admin panel. I built it on Firebase and later moved it to AWS Amplify, with Cognito and Google sign-in.

  • PTO accrues per pay period, holidays credit that day's scheduled hours, and a shortfall is covered from the balance automatically unless someone opts out for that period. The payroll export shows worked and paid hours as separate columns.
  • Employees can clock in by face at the kiosk. Recognition runs on the device, it is opt-in, consent is recorded before the camera opens, and no image ever leaves the iPad.
  • Local development runs against an in-memory mock of the backend. There are 99 unit tests and a 68-assertion verify script that run before any deploy.

React, TypeScript, AWS Amplify Gen 2. Built solo.

Enterprise Mockups

Sign-in required

enterprisemockups.web.app

The client review board. It is a Figma-style canvas where each mockup is a frame, reviewers pin comments to the exact spot, and the export includes the file, the position and the element, so the fix can be handed to a person or an AI.

  • Frames can be PDFs, single HTML files, images, live URLs, or a zipped multi-page site that navigates inside its own frame.
  • Pins are stored as fractions of the frame, so they stay put at any zoom, survive the file being replaced, and can be dragged if the design moves under them.
  • Presentation mode with authored slides, PowerPoint import that reads theme colors and master chrome, and PDF export of the whole deck.
  • A design editor inside the app, with snapping guides, rotation, groups, align and distribute, a component library, and live multi-cursor presence.
  • Undo and redo on a shared board. Each entry carries its own inverse operation rather than a snapshot.
  • Dark mode, folders, board statuses and an admin panel for managing people.
  • An admin-gated REST API and an MCP server. Deleting archives, purging is the only action that destroys anything, and the privacy page says so.

Vite, React, TypeScript, Tailwind, Firebase. Built June 2026, solo.

04 Audits

Findings from the audit work

I have audited, marked up or sped up more than twenty local-business sites this year, on WordPress, Divi, Squarespace, Wix and one franchise CMS. The clients are not named here, but the findings are real, and these are the ones worth repeating.

  1. Flooring store, Idaho

    131 of the 191 reachable pages had a canonical tag pointing at the franchise parent's website, and not one of them ranked for anything.

    Rewriting the copy on those pages was never going to work, so the plan moved to the sixty pages the store actually controls.

  2. Dog daycare, Houston

    The schema was there, but it was injected through Tag Manager, so a fetch of the server HTML made it look like there was none.

    Worth checking the rendered page before calling anything missing. The same audit also found a live search ad naming the wrong city.

  3. Dog daycare, California

    The hero image URL sat 90 percent of the way through a 391,000-character HTML file, in a style block near the end of the body, so the browser could not start loading it until it had parsed almost the whole page.

    A single preload tag in the head is the biggest speed win on that site. The WebP plugin was also producing files larger than the JPEGs it replaced.

  4. Dog groomer, Idaho

    The business had moved, and the citations had not.

    Same zip code, so a quick check looked consistent. There was also no SEO plugin installed at all, which explained why thirteen pages had no meta description.

  5. Dog trainer, Tennessee

    The live structured data had the business name spelled wrong and pointed the logo property at a featured image.

    Only the homepage had any schema, none of the twenty titles was in range, and the server would not negotiate HTTP/2 while serving 71 files per page.

  6. Dog resort, North Carolina

    The WordPress login name was being published on all 23 pages, both in the data layer and in the Twitter card.

    That is a credential-hygiene problem before it is an SEO problem. Otherwise it was the strongest site I looked at this year, scoring 79 out of 100.

  7. Healthcare marketing agency, Idaho

    Zero keywords in the top twenty. It was a standing start, not a decline.

    Most of what did rank was cardiology terms landing on the blog because the agency's name looks like the word cardiac. I did not report those as wins.

  8. Hospital, Idaho

    The hospital shares its name with four bigger places, so national search volume for its own name was meaningless.

    Positions have to come from a rank tracker located in the town itself. The word False was also printing 248 times across thirty specialty pages.

  9. Dog daycare, Texas

    The map-pack grid for dog boarding read 11 to 13 at every point in the city, including the pin on their own address.

    That is a relevance ceiling rather than a proximity problem, so service-area pages would not move it. The site had no backlinks at all, and some of the competitors above it had eight.

  10. Dog park and lodge, Washington

    Squarespace injects its own Organization schema, so the site was carrying two of them with different phone numbers.

    Nothing had been installed wrong. The platform's block and the custom block simply disagreed, across twelve pages. The custom graph now covers 23 schema types and 118 question and answer pairs.

  11. Dog daycare, Massachusetts

    Every URL with a trailing slash returned a 500, and every old WordPress inbound link had a trailing slash.

    One extensionless path also returned a 403 that nothing in the config explained. The metadata and the schema graph shipped the same day, and the hosting problems went into a fix list.

  12. Developer portfolio, Idaho

    The staging hostname was still inside the structured data on eleven pages, so the articles pointed at an author and a publisher that did not exist.

    Apart from that it was the cleanest crawl of the year: 27 pages, no faults, every image with alt text and dimensions.

05 Enterprise

SEO at national scale

The other half of my week goes to one account: a national payments processor and its co-branded programs, across four websites in the US and Canada. The work there is research, recommendations and working mockups that the client's own teams take live, so I do not name it here.

  1. Site-wide keyword architecture

    Every indexable page mapped to one target keyword, with a retain, optimize, consolidate, redirect or decommission call on each of 238 URLs.

  2. Resource and support center rebuilds

    Two pitches delivered as working mockups instead of slides, built from a harvested library of the client's real content inside the client's real header and footer.

  3. Schema and metadata for 501 pages

    One JSON-LD graph plus a rewritten title and description for every indexable page across the four sites. Each graph validated with zero errors, and the work was delivered as per-account workbooks with the issue log attached.

  4. The orphaned library

    Five category pages linked to 106 articles, but nothing linked to the category pages, because the View all controls were buttons rather than anchors. That left 87 of 102 articles with no crawlable path from their own section. Googlebot follows links and does not click buttons, so the fix was five anchors and five sitemap entries.

  5. Content plan restructure

    One page type per week per account. The template gets built once and rolls across every page of that type, instead of a page picked at random each week.

  6. FAQ program for a Canadian site

    135 questions mapped across 29 pages, 81 of them answerable from copy that was already approved, with the live site's own contradictions flagged before anything was written.

  7. Partner bank web audits

    Six-dimension scoring of a bank's public web presence, delivered as a scorecard, gap analysis and roadmap. The crawl rig is re-runnable for the next partner.

  8. Personalized marketing toolkit

    A marketing page for merchants. A code in the URL swaps in that merchant's own QR code and matches the downloadable assets to their account.

  9. A 220-page partner marketplace

    Titles, descriptions and structured data for every listing on a marketplace where 155 pages shared one title and nothing carried a canonical.

08 Process

How this works

What happens after you send me a URL.

  1. Send the URL

    Tell me what the site is for and what you have already tried. I will load the site before I reply, so the first answer is about your pages and not about web design in general.

  2. I crawl it before I recommend anything

    Every page gets checked: status, titles and descriptions with pixel widths, canonicals, structured data, internal links and images. The findings above came out of crawls like that, not out of a checklist.

  3. You get a written diagnosis

    What is wrong, why it matters, and what to fix first, in priority order. It is a document you can read and forward, not a slide deck.

  4. The build keeps your URLs

    Hand-coded pages, old URLs mapped to new ones with redirects, and metadata and structured data written from your real content. Nothing invented and nothing from a stock library.

  5. Launch gets verified

    After a push I read the live files back through every cache layer. Then the redirects, the sitemap and the structured data are checked again on the live domain.

  6. You own the files

    Plain HTML, CSS and JavaScript on hosting in your name. Any host can serve it and any developer can read it.

Common questions

Do I own the site afterward?
Yes. You get the files, and the hosting and domain stay in your name.
I am on Wix or Squarespace. Do I have to move?
No. Titles, descriptions, structured data and redirects can all be managed inside Wix through its own API, and Squarespace accepts code injection. Moving makes sense when the platform gets in the way of the content, which is what happened with the iframes above.
Can you work on my existing site instead of rebuilding it?
Most of the audit work on this page was exactly that: WordPress, Divi, Squarespace, Wix and a franchise CMS, fixed in place.
What do you need from me to start?
The URL. Access to Search Console and Analytics sharpens the priorities if you have them, but a crawl needs neither, so the first look can start with the URL alone.
